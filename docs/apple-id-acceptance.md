# Apple ID 自动签名验收

目标设备为 iPhone 15 Pro Max / iOS 18.7.8。本文不保存 Apple ID、密码、验证码、设备标识、配对文件或私钥。CI 使用本地合成数据；真实 Apple 服务和设备安装需要按下列步骤单独验收。

## 准备

1. 使用自己的账号通过 Sideloadly 安装或覆盖更新 LocSign，保留原 Bundle ID。
2. 开启 LocalDevVPN。默认设备地址为 `10.7.0.1`；其他隧道使用其实际设备 IP。
3. 准备当前手机的电脑配对 plist，在连接页完成配对和安装服务验证。
4. 准备一个可以合法使用的 IPA。当前自动申请仅支持一个主 App、无扩展/嵌套 App、未加密的单一 arm64 主程序；暂不接受 FAT 主程序和 DER entitlement。App Groups、Push、Associated Domains 等额外权限会在远端修改前被拒绝。默认保留原始 Bundle ID；0.2.3 可明确选择个人标识，原始 IPA 保持不变。不删除远端 capability/profile。

## 登录和验证码

1. 打开签名页的 Apple ID 入口，检查 Anisette 提供方地址。默认提供方为 `https://mac-ani.jkcoxson.com`。
2. 阅读并确认提供方会接收本地 UUID、ADI 注册握手消息及 ADI blob，并能看到来源 IP。可以替换 HTTPS/WSS 提供方或关闭此功能。关闭后可继续使用本机有效材料签名，或手动导入签名材料。
3. 输入 Apple ID 和密码后登录。密码在提交时从输入框清空；需要验证码时输入 Apple 提供的六位验证码。取消应结束等待，重新登录时需要重新输入密码。
4. 登录后确认免费 iOS 团队。唯一团队自动选中，多个团队需要自行选择。未申请材料时不显示预估到期日。

## 申请和签名

1. 导入 IPA、当前设备配对文件，填写设备地址并检测已配对设备。
2. 选择团队。需要独立签名标识时开启“使用个人签名标识”，等待固定标识生成并核对输入框；原标识模式则关闭此选项。点击“获取材料并签名”前会重新建立配对 TLS 并读取设备标识；设备变化应停止申请。个人模式会独立安装应用，不继承原标识应用的数据；后续更新保持相同标识。
3. 有本地匹配私钥和有效证书时优先复用。新私钥先进入本机 Keychain 再发送 CSR；后续 profile 失败保留已生成的密钥和证书供重试。
4. 只有明确的证书配额错误才请求撤销确认。检查列表中的证书名称、序列号和有效期；撤销可能影响其他已签 App 及 LocSign 自身。默认取消，拒绝后不发删除请求。确认后远端列表有变化也会停止。
5. 只有材料通过 Apple CMS、证书私钥、团队、所选目标 Bundle ID、设备及有效期校验，并实际生成 IPA 后，才显示签名文件和到期日。预检查仍核对原 IPA 权限；签名副本的应用标识和权限必须与目标匹配。
6. 取消后迟到结果不得恢复账号、替换本地材料或发布签名文件。取消无法回滚 Apple 已完成的设备/App ID 注册或证书撤销；普通取消保留待完成私钥，明确退出并清除才删除本机账号条目。

## 安装、清理和记录

### 复用本机材料

1. 至少完成一次申请和签名后，关闭自动申请或取消提供方同意，重新打开 Apple ID 签名页。本机账号和团队应仍可用于已保存材料；账号会话过期也不应阻止此路径。
2. 选择原 IPA、原配对文件和团队；若材料按个人标识申请，继续启用个人模式并使用相同目标标识。检测设备后点击“使用本机有效材料签名”。此操作不请求 Anisette 或 Apple 服务，仍需要本地 VPN 访问已配对设备。
3. 每次使用都重新验证 Apple CMS、证书与私钥、团队、Bundle ID、设备和有效期。没有材料、已到期或不匹配时应明确停止，不自动发起申请。离线校验无法查询 Apple 是否提前撤销证书，安装及启动仍以设备结果为准。
4. 在线申请失败后，本机原有有效材料应仍可复用；更换提供方不删除签名材料。需要新申请时重新同意提供方并登录。

### 安装与退出

1. 签名完成后保存 IPA，并测试安装到已配对手机。签名成功和设备安装成功分别显示。
2. 安装失败应保留可导出的签名文件，并显示安装错误；不能把上传完成当作安装成功。
3. 从主屏幕实际打开已安装 App，确认能启动。定位功能不属于本轮验收。
4. 使用“退出并清除本机账号资料”验证重新打开后需登录，无法复用该账号材料，且该账号生成的本机签名文件、到期日和安装成功状态已清除。已导出到其他位置的副本需自行管理。覆盖更新保留安装标记和资料；iOS 不保证卸载会删除 Keychain，新安装缺少本应用标记时会清理本应用专用命名空间。
5. 只记录日期、构建号、成功/失败阶段和安全错误码。不要公开截图中的账号/设备标识，不上传配对 plist、证书私钥或认证响应。

真机结果（2026-11-07，用户反馈）：Apple ID 登录成功。尚未确认是否触发二次验证；证书和描述文件申请、签名、安装及启动继续待验收。CI 通过不代表 iOS 已接受安装。

兼容性回归：0.2.0 在 Feather.ipa 预检查时提示“代码签名容器无效”。对照官方 Feather v2.9.0 发行包发现，代码签名预留区为 186,336 字节，内部有效容器为 168,327 字节，余下 18,009 字节是零填充。0.2.1 / build 7 按内部声明长度约束索引及子区块，允许有效容器后的预留填充；权限和加密限制继续生效。用户原 IPA 的版本尚未确认，更新后的实际签名与安装结果需重试记录。

0.2.1 交付验证：[最终 CI](https://github.com/kevin9525/locsign-public-build/actions/runs/42346306254) 的 179 项 XCTest、4 项打包测试及模拟器/设备构建均通过，最终未签名 IPA 的版本、资源和 CRC 已核验。详细根因与回归记录见 [Feather 兼容修复](spike/2026-11-07-feather-preflight-fix.md)；此次构建不构成真机材料申请、签名或安装成功的证据。

后续真机反馈：配对验证通过后，点击“获取材料并签名”直接显示 `The operation couldn’t be completed. (LocSign.DeveloperServicesError error 0.)`，此前未出现撤销开发证书确认列表。旧错误展示丢失具体请求步骤及 HTTP/Apple 返回码，当前无法确定远端拒绝原因。0.2.2 / build 8 为错误诊断修复，复测需记录完整新错误，或分别确认材料申请、签名、安装和启动结果。调查及验证记录见 [开发者服务错误诊断](spike/2026-11-07-developer-services-errors.md)。

0.2.2 交付验证：[CI](https://github.com/kevin9525/locsign-public-build/actions/runs/42352560129) 的 185 项 XCTest、4 项打包测试、模拟器/设备构建和打包步骤均通过。已下载最终未签名 IPA 并核验 0.2.2 / build 8、资源和 CRC。此版本确认修复的是错误信息展示；实际 Apple 拒绝原因和完整签名安装结果仍待真机反馈。

0.2.2 后续真机截图明确显示“注册应用标识失败（HTTP 409）”，USB 已确认安装版本为 0.2.2 / build 8，且未进入证书申请。用户确认允许增加独立签名标识。0.2.3 / build 9 的 202 项 XCTest、4 项打包测试、模拟器/设备构建和打包通过[CI](https://github.com/kevin9525/locsign-public-build/actions/runs/42364714322)，最终 IPA 已核验。新个人标识流程仍待真机重试；409 本身不能证明标识占用，注册额度限制也不能靠更换标识解除。详细证据与步骤见 [个人签名标识](spike/2026-11-07-personal-signing-identifier.md)。

后续真机截图已确认安装 0.2.3（9），个人标识已生成且配对通过；流程已进入“申请开发证书”，返回“Apple Developer Services 返回的数据无效”。旧错误同时覆盖证书签发响应解析与 REST 证书记录匹配，不能据此断言 Apple 未签发证书。代码检查发现匹配逻辑依赖可选的 `certificateContent`，不兼容只返回序列号等信息的证书列表。修复与验证记录见 [证书响应兼容](spike/2026-11-07-certificate-resolution.md)。具体真机响应尚未捕获。

0.2.4 / build 10 交付验证：208 项 XCTest、4 项打包测试、模拟器/设备构建及 IPA 打包全部通过[CI](https://github.com/kevin9525/locsign-public-build/actions/runs/42371240623)，最终 IPA 的版本、应用标识、资源及 CRC 已核验。更新后保留相同个人签名标识，点击“获取材料并签名”复测。若失败，请记录完整新错误和是否出现证书撤销确认；旧版已签发但未保存的证书不保证可恢复，完整真机签名/安装结果仍待确认。

0.2.4 后续反馈为“申请开发证书失败：证书签发响应格式无法识别或未包含有效的 X.509 证书”，范围缩小到证书签发响应解析或 X.509 解析。参考实现支持 PEM，而当前版本只接受 DER；两个新增回归用例已复现这一兼容缺口。0.2.5 将合法 PEM/base64 统一成经过 X.509 验证的 DER，并使用固定 C01–C09 分类区分响应结构、字段、编码及证书解析问题。真机原始响应未取得，不能仅凭旧错误确认其为 PEM。进展见 [证书响应格式](spike/2026-11-07-certificate-response-format.md)。
