# Installation over a network requires a device heartbeat

The user reproduced 0.2.7's precise error: preparing the upload directory failed with TLS receive -9806. This places the failure in the first AFC filesystem exchange after successful device authentication and service connections. The connection-page probe only opens/closes the services, so its success does not establish a successful AFC request.

Read-only comparison on the USB-connected iPhone found that USB AFC and installation_proxy do not require service TLS and work. Bonjour advertisements matching the same local pairing record's Wi-Fi identity provided the device address; the advertised service port refused a connection, while the standard lockdownd port 62078 worked. Every authenticated probe pinned the device certificate to the existing local USB pairing record before device/service requests. No pairing credential, network address or device identifier is included here.

Over the device's network interface, both services required TLS. The existing installation order completed both handshakes but the first AFC GetDeviceInfo request returned EOF. Starting only AFC also failed, ruling out the second service as necessary for this failure. Using the pair record's root identity instead of the host identity made no difference. A concurrent filtered system-log probe showed afcd interacting with com.apple.mobile.heartbeat before closing SSL; that observation alone was only a hypothesis.

The decisive comparison retained the same host certificate, pinned device trust, service order and request encoding, and added com.apple.mobile.heartbeat. After receiving Marco and sending Polo, with a background response loop, AFC GetDeviceInfo and installation_proxy Lookup both succeeded. Creating and removing one new, unique empty directory under /PublicStaging also returned status zero. The probe did not upload an IPA or submit Install. This establishes the missing heartbeat requirement for this device's network services; LocSign on LocalDevVPN still requires final device validation.

A sustained probe observed the first exchange and two subsequent Marco/Polo cycles, with a device-reported interval of ten seconds. AFC reads after both later cycles succeeded, followed by successful probe-directory creation/removal and installation Lookup. Removing heartbeat again reproduced immediate EOF. This A/B/A result rules out a one-time service startup improvement; no pairing, signing or trust configuration was changed between the comparisons.

The bounded fix will own a heartbeat for the duration of installation: complete the first Marco/Polo exchange before opening AFC; respond to subsequent Marco messages; retain the first background failure; check health before preparing upload and before submitting Install; stop and join the pump on every exit. Known heartbeat failure must not silently proceed to Install, and no automatic reconnect or Install replay is added. A confirmed Complete remains authoritative if the heartbeat closes afterward.

Stopping a heartbeat must interrupt a blocked read. A socket interrupt will only shut down the descriptor under the same synchronization used by final descriptor close. TLS cleanup remains on the service's serial I/O queue to avoid racing SSLRead with CFRelease. Existing TLS certificate validation, signing and certificate-management behavior remain unchanged. The connection-page probe retains its documented connection-only scope in this fix.
