# Installation TLS receive failure (-9806)

On 2026-11-09 the user reported `TLS 接收失败（-9806）` immediately after requesting installation of Feather.ipa in LocSign, with progress near zero. Their latest correction confirms that the separate pairing/service check succeeds and installation fails. Selecting the same pairing plist and device address again in the signing page did not resolve it. The installation button requires an existing signing output, but this alone does not establish which signing-material path succeeded.

USB read-only checks confirmed installed LocSign 0.2.6 / build 12. An authenticated, pinned TLS session successfully read device identity, started AFC and installation_proxy in the installation coordinator's existing order, opened both connections, and performed AFC GetDeviceInfo and installation_proxy Lookup. Neither service requested service TLS over USB. These results do not prove the phone's LocalDevVPN route behaves identically. No Install command, file upload, or certificate operation was issued by the diagnostic script.

The error originates in `LSDeviceSocket.readTLSLength`, shared by the authenticated lockdown session and encrypted service connections. In 0.2.6 the coordinator propagates the bare error without identifying the operation. The zero-percent progress spans session setup, service startup, connection, directory creation and the start of upload, so it cannot localize the failure.

The pairing check starts and connects each service before starting the next; installation starts both before connecting either. This is an observed difference, not a confirmed cause. The diagnostic release retains the existing ordering and trust validation. System-log observation did not yield a corresponding TLS failure; routine XPC cancellation messages are insufficient evidence of a cause. Raw system logs and pairing credentials are not retained in the repository.

The bounded change labels the failed operation and retains its underlying error. Steps distinguish device connection, pairing authentication, device identity, starting/opening each service, upload directory preparation, IPA upload, sending Install and waiting for its result. Cancellation stays cancellation. A failed attempt keeps the signed source, closes connections and does not replay Install. Only a Complete response establishes success.

Regression tests exercise the real coordinator, AFC client and installation client with network fixtures. They inject the same -9806 at different boundaries to verify localization, original error preservation, cleanup and lack of replay. They also verify Complete is required after a 100-percent progress event and that an injected CancellationError during upload does not submit Install. This is diagnostic coverage; it does not reproduce the real VPN disconnection.

Twenty-seven assertions failed within the four new diagnostic cases, showing bare TLS errors without stage/cause wrapping. All 234 baseline cases and the new success/cancellation cases passed. The retained simulator diagnostics establish the RED result; the later device build was superseded by GREEN.

The downloaded test log confirms 243 tests with zero failures. Three additional cases cover device connection, Install send failure and both real socket adapters preserving their constructor error domain/code. Four packaging tests, simulator and unsigned device builds, IPA assembly and the overall job also passed.

Delivery artifact `13648030158` was downloaded and checked: version 0.2.7 / build 13, original application identifier `com.locsign.LocSign`, nonempty executable, all three bundled Apple root certificates, third-party notices, valid archive CRC and unsigned package layout. `LocSign-0.2.7-build13-unsigned.ipa` is 12,931,495 bytes; SHA-256 is `969b1c3b14bb357d355671698d5afbe08550795bee43e1c163470b61cb745c74`. These checks verify the diagnostic build, not successful phone-VPN installation.

Scope limitation recorded during review: the existing installation client can send Install before checking cancellation if a task is cancelled immediately before submission. This release preserves propagation of existing cancellation errors; it does not implement a complete cancellation boundary or immediate interruption of socket I/O. There is currently no installer cancellation control in the UI. This pre-existing behavior is separate from the observed -9806 and remains a follow-up concern.

The second code-review pass found no release-blocking implementation issue after adding connection/send failure tests and preserving socket-constructor errors. Its documentation correction narrows the cancellation test claim to the injected upload error. The final GREEN run and artifact verification subsequently passed.
