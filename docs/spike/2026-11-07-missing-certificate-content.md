# Recovering certificate content after C03

The user reports C03 on 0.2.5: the legacy request returned a successful envelope with a `certRequest` dictionary but neither directly supported certificate-content field. This narrows the failure to the immediate-content assumption; it is not evidence of a password, pairing or PEM failure. The actual record fields are not available.

AltSign's certificate model accepts both nested `attributes` and metadata-only records. The generated DeveloperAPI client exposes `GET /v1/certificates/{id}` with explicit certificate-content fields. The repair supports nested content while preserving ambiguity checks, and uses the existing durable private key to recover certificate contents through read-only list/detail requests.

Before issuing a CSR, a saved pending key is compared against valid development certificates. If a list entry omits DER, the exact resource is queried. The response must retain its resource ID and serial, its DER serial must agree, and its certificate must match the saved private key and pass existing validity checks. Profile validation remains mandatory. More than one matching candidate is rejected.

The initial implementation saved the waiting marker after receiving C03. Independent review identified a cancellation window: both the response pipeline and guarded Keychain store reject cancelled operations, so cancellation could leave the previous key without that marker and permit another CSR on retry.

The follow-up fix persists the pending material as awaiting recovery before sending a CSR. Cancellation, uncertain network/server errors and response parsing failures retain this state. Only a definite rejection of the CSR itself clears it: a quota/Apple rejection or HTTP 4xx other than request timeout. A failure while listing certificates after successful issuance is not an issuance rejection, even if that read returns HTTP 401 or 429. The engine's generation and cancellation guards remain in place.

After a C03 response, the recovery path runs once. If content is unavailable, the pending state remains: later user retries query again without submitting another CSR or offering quota revocations for that pending issuance. The optional state field is backward-compatible with older stored keys. A successfully recovered certificate is durably stored before profile creation.

Queries cannot guarantee that Apple exposes certificate bytes. When no valid match is available, the app explicitly reports the unconfirmed issuance outcome and retains local material; it does not claim successful signing. Cancellation immediately before transmission or an offline error can conservatively remain pending because the transport cannot prove whether Apple received the CSR. This version provides no automatic reset or certificate revocation to resolve that uncertainty.
